# 設計判断: なぜ Markdown を正データにするか

本文書は、kb-harness-core が「エンティティ 1 件 = Markdown ファイル 1 件」を正データ（source of truth）とし、グラフデータベース（Neo4j 等）を採用しなかった理由を記録する。
将来「グラフ DB に移行すべきではないか」という議論が起きたときの出発点として使う。

## 1. 前提

- 正データは Markdown ファイルの frontmatter と本文である。
- `graph.json` はそこから決定論的に生成される派生物であり、手で編集しない。
- 整合性（型・述語の domain/range・タグ語彙・リンク・出典）は `kb --check` と CI で検証する。

## 2. 採用理由

### 2.1 AI エージェントが直接読み書きできる

本ハーネスの主要な編集者は AI エージェントである。
Markdown と YAML はエージェントがそのまま読み、そのまま書ける。
グラフ DB を正データにすると、エージェントの出力（Cypher 等のクエリ言語）を検証・実行する層が別途必要になり、誤ったクエリによる部分更新の危険も生まれる。

### 2.2 本文と出典が一次データである

利用側（RAG、執筆、史料考証）が必要とするのは、関係の一覧ではなく、出典付きの本文である。
グラフ DB ではノードのプロパティに本文を詰めるか、外部ファイルを参照するかになり、いずれも二重管理を招く。

### 2.3 履歴とレビューを git に委ねられる

エンティティの変更履歴、差分レビュー、ブランチによる並行作業は git がそのまま提供する。
グラフ DB で同等の履歴を持つには、バージョニングを自前でモデル化する必要がある。

### 2.4 制約検証はどのみちアプリ層に置く

述語ごとの domain/range 制約、タグ語彙、出典の実在確認といった検証は、一般的なグラフ DB の組み込み制約（一意性・存在制約程度）では表現できない。
どちらを選んでもアプリ層の検証コードが必要であり、それならば正データを単純なファイルにしておくほうが検証も再現もしやすい。

### 2.5 運用費がゼロである

常駐プロセス、バックアップ、スキーマ移行、ホスティング費用が不要である。
リポジトリを clone すれば、Python と PyYAML だけで検証・生成が完結する。

## 3. 採用しなかった選択肢

- **グラフ DB（Neo4j、Memgraph 等）**: 多段トラバースと大規模グラフには優れるが、本ハーネスが想定する規模（数百〜数千エンティティ）ではその利点が現れない。上記 2.1〜2.5 の理由により正データとしては不採用。
- **RDF ストア / OWL**: 語彙と制約を形式的に扱えるが、エージェントによる編集と本文管理には向かない。語彙の定義は `vocabulary.yml` で十分に表現できている。
- **リレーショナル DB / SQLite / DuckDB**: 集計には便利だが、本文・出典・関係を 1 ファイルにまとめる利点を失う。派生ビューとしての利用は妨げない。

## 4. 想定規模と限界

- 検証と生成はファイル数に対して線形である。数千エンティティ・数千関係までは秒単位で完了する。
- `graph.json` を人が目視で確認できるのは関係数が数千程度までである。それを超える場合は派生ビュー（第 6 節）で扱う。

## 5. 再検討の条件

以下のいずれかに該当したとき、グラフ DB を正データに据えることを再検討する。

- 関係数が数万を超え、検証や生成が実用的な時間で終わらない。
- 対話的な多段トラバース（「A の弟子の弟子のうち B 流派以外」など）が日常の主要な操作になる。
- 複数のアプリケーションが同時に書き込む必要があり、git のマージでは衝突を吸収できない。

## 6. 派生ビューとしてのグラフ DB 利用

グラフ DB を「読み取り専用の分析ビュー」として使うことは、この方針と矛盾しない。
`graph.json` を Neo4j、Kùzu、networkx などに読み込み、系譜の可視化、孤立ノードの検出、出典に依存する主張の一覧などを行ってよい。
その場合も正データは Markdown のままとし、分析結果を KB に反映するときは通常の編集手順を通す。
