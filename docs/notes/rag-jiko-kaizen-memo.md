# 考察メモ: RAG の検索を KB 自身が改善し続けられるようにするか

2026-09-29 のディスカッションの記録。omnibus-kb に SELF-INDEX（Lee ほか, "Self-Evolving Search Index", arXiv:2609.19656）を収録した際に、「kb-harness-core で RAG の自己改善を行うならどのような手法になるか」を考えた。

結論は「**失敗した問いを診断し、検索用のキーを直し、検証してから反映する周回にする。ただし検索・重みづけ・グラフ展開・評価・診断は kb-retrieval-core の責務であり、ハーネスには置かない。ハーネスが持つのは、LLM が生成したキーを KB のデータとして検査・出力する台帳と、relations から評価の問いの候補を作る仕組みと、生成を担うスキルである**」。当初は検索側の部品もハーネスに足す案だったが、同日のうちに kb-retrieval-core の存在を確かめて改めた（末尾の「再考」）。このメモは判断の経緯を残す。契約はまだ変えていない。

## SELF-INDEX の要点

文書そのものは変えず、文書ごとに検索用のキー（原文のキー 1 つと生成したキー最大 9 つ）を持たせ、LLM の Optimizer が次の周回を回す。

1. **Query Simulator**: 文書から来そうな問い合わせを作る。既存の問い合わせと語が重なりすぎるものは除く。
2. **Self-Diagnosis**: 実際に検索し、目的の文書と一緒に引っかかるキー（紛らわしい相手）を記録して失敗を診断する。
3. **Self-Revision**: 失敗の原因になった文書のキーだけを改訂する。戦略は事前に決めない。
4. **Self-Validation**: 改訂案を Faithfulness（文書に根拠がある）・Specificity（その文書に特有）・Separation（他のキーと区別できる）の 3 基準で検証し、合格したものだけを反映する。

検索器は BM25 でも密ベクトルでもよく、検索エージェントの BrowseComp-Plus で正答率 36.51% → 64.94% と報告されている。発想の源は、文書から問い合わせを予測して足す doc2query（2019）にある。一度生成して終わりにせず、失敗から直して検証する周回にした点が新しい。

## ハーネスにすでにある部品

| 部品 | 役割 | SELF-INDEX で対応する段 |
|---|---|---|
| `evals/rag-eval.yml` | `query` / `expected` / `evidence` / `history` / `gap` | 評価データ |
| `rag-tester` エージェント | KB だけで回答を試みて判定し、新規クエリを 5 件足す | Query Simulator（人の判断つき） |
| `kb eval smoke`（`evaluation.rank_documents`） | 根拠が字面検索の上位 `--limit` 件に入るか | 診断の入口 |
| `kb eval summary` | 過去 OK → 最新非 OK の退行検出 | 検証の一部 |
| `gap` の語彙（`retrieval` / `missing-text` ほか） | 失敗の原因分類 | 修正先の振り分け |
| `expand-kb` スキル | `gap` を拾って直す | Revision（人手） |
| `staging.py` | spec → 計画 → 一時 KB で全体検証 → 適用 | Validation の器 |

欠けているのは、(1) 生成したキーを置く場所、(2) 導入先の実際の検索器に差し替えられる評価、(3) 紛らわしい相手を返す診断、(4) 退行ゼロを条件にした自動の検証ゲートである。

## 観察された問題

omnibus-kb（be567f8、`content_root` 配下の Markdown 216 件）で、`kb eval smoke` と同じ `rank_documents`（文字 bigram の重なり、title を 2 倍に重みづけ、上位 5 件）を使い、正解の根拠が機械的に決まる 3 種の問いを作って測った。

| 問いの種類 | 作り方 | 上位 5 件に根拠が入った割合 |
|---|---|---|
| 別名 | 各エンティティの `aliases` の各値 X について「X とは」、根拠はそのエンティティ | 357 / 517（69%） |
| 作り手 | `created-by` の各エッジについて「<始点の title> を作ったのは誰か」、根拠は終点 | 8 / 15（53%） |
| 所属 | `part-of` の各エッジについて「<始点の title> は何の一部か」、根拠は終点 | 23 / 33（70%） |

別名の失敗は、`desert rose`（adenium）、`Backpropagation` / `BP`（backpropagation）、`Agent Execution Graph` など、英字の短い別名に集中する。`aliases` は frontmatter として本文に含まれているが、title のような重みを持たないため、どこにでも現れる bigram に埋もれる。同じ問いで、title の重みづけの対象に `aliases` を加えた版を試すと **515 / 517** になった。ただしこの問いは別名から作っているので、別名がキーとして働くかだけを測っており、一般の検索精度の指標ではない。

作り手と所属の失敗は、答えが本文ではなく relations の先にあることによる。例は「アリアプロII PEシリーズを作ったのは」→ マツモク、「攻殻機動隊を作ったのは」→ 士郎正宗、「Omarchy を作ったのは」→ DHH。字面検索はグラフをたどらないので、始点の文書は引けても終点に届かない。

また、omnibus-kb には `evals/rag-eval.yml` がまだ無く、この周回は一度も回っていない。

## 対応の選択肢

**キーの置き場所**

- (a) 既存の `aliases` / `description` に書く。仕組みは増えないが、人が書く正本に機械の候補が混ざる。`description` は index.md にも転記される読み物なので、検索語を詰めると読みにくくなる。
- (b) エンティティとは別の台帳（例: `<content_root>/retrieval-keys.yml`）に、エンティティのパスごとのキーと出どころ（元になった失敗・日付・生成者）を置く。`kb validate` が検査し、`kb sync` が graph.json と OKF 出力に載せる。ビューと同じく、生成物ではなく検証つきでコミットする台帳にする。
- (c) `kb sync` のたびに生成する。LLM の出力は決定的でないため、`kb sync --check` の再現性が壊れる。

**問いの出どころ**

- (d) relations から構造の問いを決定的に作る（作り手・所属など）。正解の根拠が機械的に決まり、LLM が要らない。
- (e) 本文から LLM が問いを作る（rag-tester の新規クエリ生成の拡張）。SELF-INDEX と同じく、語の重なりが大きいものは除く。
- (f) 修正用の問いと、合否を決める固定セット（`evals/rag-eval.yml`）を分けるか、混ぜるか。

**検索器**

- (g) 内蔵の `rank_documents` を改良する（別名・`description` の重みづけ）。
- (h) 検索器を差し替え可能にする（内蔵 bigram、BM25、導入先のコマンド）。導入先が実際に使う検索器で測れなければ、直しても本番は良くならない。
- (i) 1〜2 段の relations をたどる検索をハーネスが持つ（作り手・所属の失敗への対処）。

**診断と検証**

- (j) 失敗を構造化診断（仮称 `eval.retrieval.outranked_by`）で返し、根拠より上に来た「紛らわしい相手」を記録する。
- (k) 3 基準をハーネスで検査する。Faithfulness はキーの語が本文か出典のメモに現れるかという決定的な代用で見て、曖昧なものは evidence-reviewer に回す。Specificity は他エンティティの title・`aliases`・キーとの重複検査（`aliases` の重複検査を流用）。Separation は一時 KB で修正用の問いと固定セットの両方を検索し直し、目的の順位が上がり、他に退行が出ない案だけを採る。

**層の分け方**

- (l) 周回全体をハーネス本体に入れ、LLM もハーネスから呼ぶ。
- (m) 決定的な部分（台帳の検査・出力、検索器、診断、構造の問い、検証ゲート）を本体に、生成（本文からの問い、キーの修正案、曖昧な Faithfulness 判定）をスキル（仮称 `tune-index`）とエージェントに置く。

## 判断

- **今やる候補: (g) の別名の重みづけ。** 観察の 357 → 515（/ 517）が示すとおり、既存の `aliases` を検索キーとして効かせるだけで大きく改善し、新しい契約を要らない。`description` も同じ扱いにするかは、固定セットで測ってから決める。
- **今やる候補: (d)。** 構造の問いは決定的に作れ、正解も決まり、omnibus-kb に最初の `evals/rag-eval.yml` を与えられる。ただし固定セットに入れる問いは人が選ぶ（(f) の分離のため）。
- **採る方針: (b)(f)(h)(j)(k)(m)。** 自動の修正は `gap: retrieval` にだけ当て、`missing-text` / `missing-entity` / `missing-relation` は出典が要るので従来どおり expand-kb に回す。出典第一の KB では、本文と事実を自動で書き換えないことが本質である。キーは検索の入口であって回答の根拠ではない、と契約に書く。修正用の問いと固定セットは分ける。同じ問いで直して同じ問いで測ると、その問いに過適合するだけだからである。
- **見送る: (a)。** 人が確かめたキーだけを `aliases` に格上げする経路は (b) の上に作る。再開条件は、台帳を導入しないまま別名の追加だけで固定セットが十分に通るとわかったとき。
- **見送る: (c)。** `kb sync --check` の再現性と両立しない。
- **見送る: (l)。** ハーネスは決定的でドメインに依存しない本体であり、LLM の呼び出しを持たない。再開条件は、ハーネス本体が LLM を呼ぶ機能を持つと別途決めたとき。
- **保留: (i)。** 下の未決事項に回す。

## 未決事項

- **relations をたどる検索をハーネスが持つか。** 作り手 8/15・所属 23/33 の失敗は、キーを直しても解決しない。2 段までの `part-of` をたどる機能は [軽量オントロジーのメモ](keiryo-ontology-memo.md) でも条件つきで触れている。ハーネスの `rank_documents` は導入先の検索器の代理でしかないので、ここに入れても本番の RAG が同じことをする保証はない。graph.json を使う消費者側の仕事とみるか、評価だけでも持つか。
- **キーの台帳のスキーマ。** 1 エンティティあたりの上限（SELF-INDEX は 10）、キーの言語、出どころの必須項目を、ハーネスが決めるか `kb-domain.yml` で導入先に委ねるか。
- **`description` を検索の重みづけに含めるか。** 含めると検索は強くなるが、`description` を検索語で膨らませる誘因になる（`validation.description.long` の WARNING と緊張する）。
- **周回の停止条件と費用。** 固定セットの成功率が目標に達したとき、改善が止まったとき、予算に達したときのどれで止めるか。
- **固定セットの作り手。** 構造の問いを機械で作り、人が固定セットに選ぶ手順にするか。rag-tester が足す新規クエリとの関係。（新規クエリの題材の取り方は、2026-09-30 の再考で決着した）

## 再考（同日）: kb-retrieval-core との分担

上の判断は、兄弟パッケージ kb-retrieval-core（5fe691b、v0.2.0 以降の `main`）を見ないまま書いていた。その `docs/ARCHITECTURE.md` は、ハーネスの責務を「KB の作成・検証と graph.json の生成」、kb-retrieval-core の責務を「スナップショットの読み込み・分割・索引・検索・グラフ展開・Evidence Packet の組み立て・検索評価」と定め、LLM とプロンプトを入れず、索引を再生成可能な派生物とすることを不変条件にしている。ハーネスの `kb eval smoke` は検索可能性の退行を見る簡易なスモークであって、検索器ではない。

**当初「欠けている」とした部品の多くは kb-retrieval-core にすでにある。**

| 当初の案 | kb-retrieval-core の現状 |
|---|---|
| (g) 別名の重みづけ | 実装済み。entity 検索の重みは title 8、aliases 7、description 2、tags 2 |
| (h) 検索器の差し替え | lexical / vector / hybrid と RRF |
| (i) relations をたどる検索 | `--expand-graph`（1 段、既定は無効） |
| (j) 失敗の診断 | Recall@k・MRR、失敗した問いごとの返却パス、`kind` 別集計。紛らわしい相手の明示はない |
| (f) 修正用と判定用の分離 | vector の採用規則が、開発用と採用判定用のケースの分離を求めている |
| (k) の Separation | `compare_evaluations` による前後比較 |

**実測。** 観察の節と同じ機械生成の問い 565 件を `kb-retrieval eval`（lexical、k=5）で評価した。

| 問いの種類 | `kb eval smoke` | kb-retrieval-core | 同 `--expand-graph` |
|---|---|---|---|
| 別名（517） | 357 | 386 | 377 |
| 作り手（15） | 8 | 5 | 7 |
| 所属（33） | 23 | 18 | 25 |

グラフ展開は relations の先にある答えに効き、別名の問いはわずかに下がる。展開を既定で無効にし、問いの種類で選ぶという kb-retrieval-core の設計と整合する。

**互換性の欠け。** この測定は、omnibus-kb をそのまま読み込めなかったため、一時的に直したコピーで行った。(1) ハーネスは契約どおり graph.json に `views`（有効時）と `predicates`（`broader` / `maps_to` があるとき）を出すが、kb-retrieval-core のローダーは nodes / edges / claims 以外のトップレベルを拒否する。(2) ハーネスは `references.yml` の `year` の型を制約せず、omnibus-kb の 494 件中 46 件が引用符つきの年だが、kb-retrieval-core は整数以外を拒否する。いずれも kb-retrieval-core の `docs/ISSUES.md` に Issue #17・#18 として記録した。

**改めた分担。**

- **kb-retrieval-core**: 検索・重みづけ・グラフ展開・評価・前後比較。自己改善のために足すのは、失敗した問いで根拠より上に来た「紛らわしい相手」を評価レポートに出すこと（Issue #19、範囲は未確定）。
- **ハーネス**: 生成したキーを KB のデータとしてコミットする場合の台帳の検査と、graph.json など公開の交換形式への出力。relations から評価の問いの候補を作る仕組み。生成（本文からの問い、キーの修正案）を担うスキル（仮称 `tune-index`）。`kb eval smoke` はスモークにとどめ、第二の検索器に育てない。
- **利用側の RAG アプリ**: 回答生成と回答の質の評価（kb-retrieval-core の規定どおり）。

**判断の改訂。**

- **取り下げる: (g)（`kb eval smoke` の別名の重みづけ）。** 本番の検索器では実装済みで、スモークを強くしても利用者の検索は良くならない。再開条件は、`kb eval smoke` の偽陽性・偽陰性が運用上の問題になったとき。
- **移す: (h)(i)(j) は kb-retrieval-core の範囲。** (j) のうち紛らわしい相手の明示は、同パッケージの Issue #19 とする。
- **維持する: (b)(d)(f)(k)(m)。** キーの台帳がどこにあるべきかは、kb-retrieval-core の不変条件からも支持される。LLM が生成したキーは再生成できないので、同パッケージの「再生成可能な派生物」である索引には置けず、KB の正本データとしてハーネスが検査し、交換形式に載せるしかない。kb-retrieval-core がそれを読むには、入力契約への追加（重みつきの entity フィールドとして扱うか）が要る。
- **未決事項の「relations をたどる検索をハーネスが持つか」は、持たないで決着した。** kb-retrieval-core の `--expand-graph` が担う。

**未決事項への追加。**

- キーの台帳を kb-retrieval-core に渡す交換形式（graph.json のノードに載せるか、別ファイルか）と、その入力契約の変更をどちらのパッケージの変更として先に起こすか。
- ~~`references.yml` の `year` の型をハーネスが制約するか~~ → 制約しないで決着。kb-retrieval-core が数字だけの文字列を整数として受けるよう直した（同 Issue #18、523a2d2）。

## 再考（2026-09-30）: 新規の問いが答えられる問いに偏る

omnibus-kb で `test-rag` を回した際の観察と判断。

**観察。** 固定セットは 2 回続けて全問 OK だった（2026-09-29 に 43 問、2026-09-30 に回帰 14 問と新規 5 問）。`test-rag` は新規の問いの題材を「KB 内の実エンティティから採る」ので、作った時点で答えがあると分かっている問いになりやすい。これでは欠落を測れない。同じ回に、シンガポール料理の本文が「国民食の一つ」とする海南鶏飯にエンティティが無いことが分かった。この欠落は、列挙の問いを作る過程で偶然に見つかったものである。

**選択肢。**

- (q) 題材の取り方は変えず、全問 OK が続いたら全問再評価の頻度を上げる。同じ偏りの問いを繰り返すだけになる。
- (r) 新規の問いのうち 1 件以上を「KB の境界の問い」にする。題材は KB の中の手がかりから採る。本文で言及されているがエンティティの無いもの、収録済みのエンティティにありそうだが relations に無い関係などである。学習知識から題材を作らないので、「KB だけを根拠にする」という制約と両立する。
- (s) 外部の一覧（explore-kb の差分）から問いを作る。KB の外の知識を持ち込むことになり、`test-rag` の制約と衝突する。未知の候補の発見は explore-kb の役割である。

**判断。** (r) を採る。境界の問いが回答不能や曖昧になるのは想定どおりであり、`gap` を付けて拡張ループ（expand-kb）に渡す。`expected` には答えに要る情報を書き、KB に無い部分はその旨を書く。`evidence` には手がかりのあったファイルを挙げる。(q) は見送る。再開条件は、境界の問いを混ぜても全問 OK が続くとき。(s) も見送る。再開条件は、KB の中の手がかりが尽きるほど KB が網羅的になったとき。

上の未決事項「固定セットの作り手」のうち、`test-rag` が足す新規の問いの題材の取り方は、この判断で決着した。構造の問いを機械で作るかは、引き続き未決である。
