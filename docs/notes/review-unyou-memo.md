# 考察メモ: 大量の AI 生成変更をどうレビューするか（Claude Code チームの記事から）

2026-10-17 のディスカッションの記録。Claude Code チームが自らのコードレビュー手法を紹介した記事 "Solving code review at Anthropic"（https://claude.dev/blog/solving-code-review-at-anthropic/）を読み、ハーネスに反映できる点を整理した。問いは「この記事の内容をハーネスに反映できる点はあるか」。

結論は「**変更のリスク階層の文書化と、レビューの収束ルールの 2 点を取り込む候補とし、着手は保留する**」。このメモは観察と判断の経緯だけを残し、実装はしていない。`BACKLOG.md` への起票もしていない（着手を決めた時点で起こす）。

記事は要約ツール越しに読んだ。数値と表現は原文で確かめてから引用すること。

## 記事の要点

- 変更の大半を AI が書く前提で、人間は全行を読まず、機械に読解の大半を任せ、判断と責任に集中する。
- 変更のライフサイクルに層を重ねる（事前検証、必須 CI、AI レビュー、セキュリティレビュー、リスクに応じた人間の承認、段階的リリース、巻き戻し）。どの層も一部しか捕まえないが、全部をすり抜けるものは少ない。
- 人間の承認数は、リスク階層で決める。階層は作者ではなく**変更内容**で決める。エージェントの承認は人間の承認に数えない。承認は特定のコミットに対するもので、新しいコミットで取り消す。
- 過去のインシデントやリバートを評価セットにし、レビュアーを毎日採点する。指摘のノイズ（否定された・重要でないとされた）も測る。
- 作者エージェントとレビュアーエージェントが延々と往復する問題がある。指摘の約 59% は最初のパスで既に存在していた古いバグだった。3 ラウンドで方針の見直しを求める、2 回目以降は差分だけを再レビューする、指摘済みの内容を繰り返さない、バグの種類で指摘して全箇所を直させる、といった対策で、1 ラウンドでの合格が 65% から 78% に増えた。
- 「land したら own する」。変更を小さく保ち、すべてを可逆にする。

## ハーネスの現状

実測ではなくリポジトリの確認による。

| 記事の要素 | ハーネスの現状 |
|---|---|
| 必須 CI | `validate.yml` が pytest を回す。導入先には `kb validate` / `kb sync --check` と pre-commit hook のテンプレートがある |
| 独立したレビュー層 | `review-evidence` / `evidence-reviewer`、`review-entity-model`、`audit-harness` |
| 評価セット | `evals/rag-eval.yml` と `test-rag`。懸念台帳（`concerns/`） |
| リスク階層 | 無い。エンティティ追加も語彙の変更も、同じ手順で扱われる |
| `REVIEW.md` | 無い（リポジトリ直下に存在しない） |
| PR テンプレート・CONTRIBUTING | 無い |
| レビューの収束ルール | `expand-kb` と `review-evidence` には、修正ループの上限や打ち切りの記述が見当たらない（grep で該当なし） |
| 可逆性 | 固定コミットでの配布。導入先で `apm.yml` のコミットを戻せば巻き戻せるが、手順としては書かれていない |

## 対応の選択肢

**A. 導入先向けにリスク階層を文書化する**
- 例: 低 = `Note` の追加・誤字修正（`kb validate` が通れば足りる）、中 = 通常のエンティティ追加（`review-evidence` を通す）、高 = `vocabulary.yml` の語彙変更・Claim の status 変更・`kb-domain.yml` の変更（人間の確認を必須にする）。
- 利点: `add-entity` / `expand-kb` が「どこまで審査するか」を決める根拠になる。置き場は `docs/integration.md`。
- 欠点: 階層の線引きは導入先で変わりうる。ハーネスが決めると押しつけになる。雛形として示し、上書きできる形にする必要がある。

**B. 導入先向けの `REVIEW.md` 雛形を配る**
- 繰り返し出る指摘（出典のない断定、確度の付け方、括弧禁止、孫引き）を移す先を用意する。
- 利点: 導入先ごとのレビュー観点が `review-evidence` に届く。
- 欠点: `review-evidence` が `REVIEW.md` を読む手順を足さないと効かない。読ませる手順の追加は、ランタイム非依存の方針（能力で書く）に沿って書く必要がある。

**C. 見逃しをレビューに戻す手順を書く**
- `review-evidence` が見逃して後で見つかった誤りを、懸念台帳か評価セットに戻す。
- 既存の「RAG の自己改善」の項目と重なる。重複を避けるため、そちらの設計が進んでから統合する方がよい。

**D. レビューの収束ルールをスキルに入れる**
- `review-evidence` と `expand-kb` の修正ループに、ラウンド数の上限、差分のみの再審査、指摘済みの内容を繰り返さない、バグの種類で指摘する、を書く。
- 利点: 手順の追記だけで済み、コードは要らない。エージェントが修正と再審査を繰り返す場面は実際にある。
- 欠点: ハーネスで実際に往復が膨らんだ実測がまだ無い。効果は仮説である。

**E. 指摘のノイズと見逃しを測る**
- `evidence-reviewer` の指摘を「修正された / 否定された / 重要でない」に分類して記録し、集計する。
- 利点: レビュアーの改善に根拠が出る。
- 欠点: 記録と集計の仕組みが要る。エンティティ追加の規模では、集計できるほどの母数が集まるかも分からない。

**F. ハーネス自身の PR 運用を整える**
- PR テンプレートに「Testing / Risk / How to revert」を加える。AGENTS.md に、変更前に走らせるチェックを書く。固定コミットでの巻き戻し手順を `docs/integration.md` に書く。
- 利点: 軽い。記事の「すべてを可逆にする」に直接当たる。

**取り込まない案**
- マージキュー、フィーチャーフラグ、段階的リリース、オンコール。アプリケーションの運用が前提で、KB ハーネスには合わない。
- 複数エージェントの投票によるレビュー。サブエージェントを任意とするランタイム非依存の方針（AGENTS.md）と衝突する。

## 判断

- **取り込む候補: A と D。** A は文書だけで済み、導入先の判断を助ける。D は手順の追記だけで済み、既存の修正ループに直接効く。
- **条件つきで保留: B。** A の階層が決まってから、`REVIEW.md` に何を書くかを決める。
- **見送り: C は「RAG の自己改善」の設計に統合してから。E は効果の根拠がない。** C と E の再開条件は、`review-evidence` の指摘が実際に否定・見逃しされた事例が、懸念台帳か `evals/` に一定数たまったとき。
- **F は別件で足りる。** 判断を伴わない整備なので、メモを経ずに `BACKLOG.md` の 1 行で済む。

着手前に確かめること:
- 記事の数値と表現を、原文で確かめる。
- `expand-kb` と `review-evidence` で、修正ループが実際に何ラウンドまで回っているかを、導入先（omnibus-kb）の運用記録から確かめる。D の効果の見積りに要る。
