# 考察メモ: 全体を先に設計せず、関係をあとから見出すアプローチ

2026-09-25 のディスカッションの記録。[軽量オントロジーの考察メモ](keiryo-ontology-memo.md)の続き。例は omnibus-kb から取っている。

このメモの「段階 0〜1」を機械的に支える層として、ビュー（`kb-domain.yml` の `views.root`、[設定リファレンス](../configuration.md#ビュー任意)）を実装した。出典で支えられた事実はエンティティに、書き手の見方による束ねはビューに置き、ハーネスはビューをエンティティへ書き戻さない。問いは「軽量オントロジーは新しい関係を発見する基盤になりそうだが、発見した関係をどう記述するか。ファセットのようなものになるのか」。

## 「あとから見出す」は無設計ではない

関係をあとから見出すには、見比べられる形で記述されていることが必要である。発見とは反復に気づくことで、反復は記述が揃っていて初めて見える。したがって「最初に全体を設計しない」は「何も決めない」ではなく、**比較可能性だけを先に決める**ということである。

この KB がすでにやっているのはそれである。型、4 つの述語、`title` / `description` / `sources` の必須化。これらは世界の構造を決めていない。あとで並べて見られる形を決めているだけである。セマンティックレイヤーを書いたあとで DRY と情報隠蔽に線が引けたのは、三つとも同じ形式で `description` が書かれていて、「一度定義して各所で使う」という共通項が見えたからである。

先例として Kimball の適合次元（conformed dimension）とバスマトリクスがある。全社モデルを最初に作らず、業務プロセスごとにファクト表を積み上げる。ただし日付・商品・顧客といった軸だけは先に揃えておく。そうすれば独立に作ったマートがあとから結合できる。設計するのは軸、発見するのは事実。「あとから見出す」アプローチが実務で生き残った形である。

## 発見される「関係」は三種類ある

この KB で実際に起きたことを分類すると、発見されるものは一枚岩ではない。

- **(a) 既存の述語に収まる二項関係。** スノーフレークスキーマ `derived-from` スタースキーマ。書いた瞬間に述語が決まる。発見というより記入で、問題は起きない。
- **(b) 複数のエンティティに共通する性質。** DRY・セマンティックレイヤーが共有する「一度定義して各所で使う」原則。A と B の関係ではなく、ある性質を持つものの集合である。`related-to` の線二本で書けるが、本当は「集合に属する」という一項の述語、つまり属性である。
- **(c) 既存の述語では意味が言えない、方向のある関係。** Business Objects のユニバース（1991）と dbt Semantic Layer の関係は「派生」ではなく「同じ問題の再発明」である。ソグド文字→ウイグル文字→モンゴル文字→満洲文字の系譜は `derived-from` で形は書けるが、「借用」「改良」「継承」の区別は落ちる。

三つは異なる容器を必要とする。ファセットが効くのは (b) だけである。

## ファセットは何に向き、何に向かないか

ファセット分類は「全体を先に列挙しない」ために発明された。ランガナータンのコロン分類（1933）は、デューイのように全分類を木として先に決める代わりに、独立した軸をいくつか決め、個々の資料はその軸上の値の組み合わせで記述し、組み合わせは検索時に作る。

ファセットとスタースキーマの次元は同じものである。エンティティが事実で、ファセットが次元表。

ただしファセットの型は「エンティティ × 値」であって「エンティティ × エンティティ」ではない。

| 容器 | 表せること | 表せないこと |
| --- | --- | --- |
| ファセット（タグ・フィールド） | ある軸での値。集合への所属。「これは cs 分野」「これは原則、あれは技法」 | 方向。二者のあいだの固有の意味。「A が B を反駁した」 |
| 述語（エッジ） | 方向のある二項関係。検証器で domain / range を弾ける | 関係の理由。出典（この KB のエッジは `sources` を持てない） |
| ノード（関係の実体化） | 関係そのものに本文と出典を持たせられる。多項でもよい | グラフがハブだらけになる。概念の増殖 |

(b) の「共通する性質」はファセットで書くのが正しく、(c) の「方向のある新種の関係」はファセットには入らない。

## 発見した関係は、成熟度に応じて容器を変える

述語を増やさないという方針を守りながら (b) と (c) を書く手順。

### 段階 0: 捕捉

`related-to` を一本張り、「関連項目」に一文で理由を書く。安く、あとで消せる。

規約を一つ足す。**その線が出典に基づくのか、書き手の比較から出た解釈なのかを、一文の中で言う。** 「DRY と通じる」が出典に書いてあるのか、書き手が思いついたのか、今の書き方では読み手に分からない。発見された関係のほとんどは後者で、本来は Claim の領域である。

### 段階 1: 反復したら、性質として括る（ファセット化）

同じ種類の共通項が複数のエンティティに現れたら (b) である。書き方は二通りあり、この KB にはすでに暗黙の使い分けがある。

- 値に説明が要らないなら**タグ**。`cs` `cooking` がそれ。
- 値そのものに本文と出典が要るなら**ハブとなる Concept ノード**を立て、`part-of` で繋ぐ。客家料理がそれ。「料理系統」というファセットの値がページを持っているからノードになっている。

「一度定義して各所で使う原則」が今後も出てくるなら、Concept として立てて DRY やセマンティックレイヤーから `related-to` を張る。**述語は増えない。ノードが増える。** 関係の新種を述語ではなくノードで受けるのが、軽量路線での答えである。

閾値は未決。目安は「三つ以上で括る」だが、ハブ Concept を立てるコスト（出典を揃えて本文を書く）を考えるともっと高くてよい可能性がある。

### 段階 2: 方向と意味が固有で、しかも反復する

(c) のうち「借用 / 改良 / 継承」のように区別が問い合わせに効く場合だけ、述語の候補になる。判定基準は厳しくてよい。**検証器に何かを弾かせたいか。方向をたどる検索が必要か。** どちらも否なら Note か Article で書く。BACKLOG の「文字の系譜を比較する Note」はこれで、系譜という多項の関係を述語で無理に表さず、一本の読み物として実体化している。

## ファセットにも増やしすぎの罠がある

ファセットが述語より安全とは限らない。値が増殖し、表記が揺れる（「PE / ポリエチレン / LDPE」）。だからファセットの値にも統制語彙が要り、それが `vocabulary.yml` の `tags` 一覧の役割である。

述語を少なく保つのと同じ理由で、**ファセットの軸も少なく保つ**。軸を増やすのは、その軸で絞り込む問い合わせが実際に来たときだけ。今の KB は「分野」の一軸だけで、歴史なら「時代」、cs なら「原則か技法か成果物か」が次の候補になり得るが、RAG テストがその問いで落ちるまでは足さない。

## まとめ

- 「あとから見出す」に必要な先行設計は、世界の構造ではなく比較可能性。型・少数の述語・必須フィールドがそれで、Kimball の適合次元と同じ発想。
- 発見される関係は「既存述語に収まるもの」「共通する性質」「新種の方向ある関係」の三種。ファセットが受け持つのは二番目だけ。
- 軽量オントロジーで新種の関係を書く方法は、述語の追加ではなく**ノード化**。値に説明が要らなければタグ、要ればハブ Concept、多項で語りが要れば Note / Article。
- 規約を一つ足すなら、発見した関係が出典由来か解釈由来かを「関連項目」の一文で明示すること。
