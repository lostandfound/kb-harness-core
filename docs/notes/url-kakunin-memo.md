# 考察メモ: 出典 URL の到達確認が遅く、結果が揺れる

2026-09-27 のディスカッションの記録。omnibus-kb にエンティティを 1 件（出典 6 件）追加した際、add-entity スキルの手順 7 で `kb validate --check-urls` を回したところ、2 分で終わらずバックグラウンドに回すことになった。問いは「`--check-urls` に時間がかかりすぎるのは問題ではないか」。

結論は「**確かめる対象を絞れるようにし、並列に確かめ、HEAD の 404 は GET で確かめ直す。一時的な失敗の扱いは保留する**」。契約は [CLI リファレンス](../cli.md) の `kb validate` 節が正本である。このメモは判断の経緯を残す。

## 観察された問題

omnibus-kb（`references.yml` 369 件、エンティティ 110 件程度）で、v0.9.1 以降の `main`（37390cc）の `check_urls()` を 1 回実測した。

| 項目 | 値 |
|---|---|
| 所要時間 | 約 305 秒 |
| HTTP での確認 | 386 件（異なる URL は 383 件） |
| DOI レジストリでの確認 | 15 件、計 3.5 秒 |
| 5 秒を超えた確認 | 4 件 |
| ERROR | 17 件 |

遅さはタイムアウト待ちではなく件数の積み重ねである。1 件あたり平均 0.8 秒で、全部を順に確かめている。

ERROR 17 件を同じ UA で HEAD と GET に分けて確かめ直すと、3 種類に分かれた。

| 分類 | 件数 | 例 |
|---|---|---|
| 確かめ直すと HEAD も GET も 200（一時的な失敗） | 5 | en.wikipedia.org、kaken.nii.ac.jp、baijiahao.baidu.com |
| HEAD も GET も 403（ボット対策、または実行環境のプロキシ） | 10 | github.com（6 件）、britannica.com、powo.science.kew.org、chippewaboots.com |
| HEAD は 404、GET は 200 | 2 | tower.jp、greensnap.jp |

同じ日の 1 回目の実行では、ERROR は tower.jp の 1 件だけだった。つまり、同じ KB に対して結果が実行ごとに揺れる。

## 何が困るか

- **追加 1 件の確認に KB 全体の時間がかかる。** add-entity / find-book / find-paper の各スキルは、出典を足すたびに `--check-urls` を回す手順になっている。確かめたいのは足した数件なのに、待ち時間は KB の大きさに比例して伸びる。
- **時間がかかる確認は省かれる。** 省かれると、新しい出典の実在確認という本来の目的が果たされない。
- **関係のない ERROR が混ざる。** 全件を確かめると、既存の出典のリンク切れや一時的な失敗が並び、足した出典の問題が埋もれる。
- **HEAD の 404 で誤判定する。** `_url_reachable()` は HEAD が 403 / 405 のときだけ GET で確かめ直し、404 はそのまま到達不能とする。この挙動は R6 のテスト（`tests/test_validation_gaps.py` の「HEAD が 404 なら GET にフォールバックせず到達不能」）で固定されていた。HEAD に 404 を返し、GET には 200 を返すサイトが実在する。

## 対応の選択肢

**対象の絞り込み**

- (a) `kb validate --check-urls` に `--for ENTITY` と `--ref ID`（どちらも複数指定可）を足す。検証本体は従来どおり KB 全体に行い、URL の確認だけを指定した対象に絞る。
- (b) `kb reference check ID... / --for ENTITY` を新設する。`kb reference show` と形は揃うが、エンティティの `sources` に直接書かれた URL は出典レジストリの外にあり、`reference` の下に置くと守備範囲がずれる。
- (c) `--changed` で、git の差分に現れたエンティティと出典だけを確かめる。pre-commit には最も合うが、ステージ済みか作業ツリーかの意味の決定と、git 必須化が要る。

**速度**

- (d) スレッドで並列に確かめる。同じホストへの同時接続は少数に抑え、ボット対策を刺激しない。
- (e) 1 回の実行の中で、同じ URL・同じ DOI を 1 回だけ確かめる。
- (f) 確認した日時を記録し、最近確かめた URL を飛ばす。BACKLOG の「到達確認の記録」（`scripts/refs_health.py` の統合）と重なる。

**誤判定**

- (g) HEAD が 404 のときも GET で確かめ直す。
- (h) 一時的な失敗（タイムアウト・接続失敗・429・5xx）を 1 回だけ確かめ直す、または DOI レジストリに届かないときと同じく WARNING に落とす。

## 判断

- **今やる: (a)。** 既存の手順（add-entity の手順 7 など）は `kb validate --check-urls` を呼んでおり、そこにオプションを足すだけで済む。`--for` / `--ref` は `--check-urls` と組でしか意味を持たないので、単独で渡したら引数の誤りにする。指定したエンティティが引く出典は `kb reference show --for` と同じ規則（`sources` の `ref:` と本文の「（出典: id）」）で集め、エンティティの `sources` に直接書かれた URL も確かめる。見つからない出典 ID やエンティティは ERROR にする。黙って確認を飛ばすと、確かめたつもりで確かめていない状態になるためである。
- **今やる: (d) と (e)。** 全件を確かめる場合も縮めたい。出力の順序は従来どおり走査順に保ち、並列化で結果の並びが揺れないようにする。
- **今やる: (g)。** R6 で固定した挙動を覆す。代償は、本当に消えたページに 1 回余分に GET を送ることだけで、誤判定を 1 件減らす利益の方が大きい。
- **見送る: (b)。** 理由は上記。`kb reference show --for` との対称性は、同じ `--for` という名前と同じ出典の集め方で保つ。
- **見送る: (c)。** 再開条件は、pre-commit hook で URL 確認を回したいという要望が出たとき。
- **見送る: (f)。** 記録の置き場所（`references.yml` の `checked` を機械が書き換えるか、別ファイルか）を先に決める必要がある。BACKLOG の既存項目で扱う。
- **保留: (h)。** 下の未決事項に回す。

## 未決事項

- **一時的な失敗を ERROR にするか。** 実測では ERROR 17 件のうち 5 件が確かめ直すと 200 で、実行ごとに結果が揺れた。DOI については「レジストリに届かないものは登録の有無が分からないので WARNING」とすでに決めており（CHANGELOG の Unreleased）、同じ考え方を HTTP にも当てるかどうか。当てるなら「404 / 410 は ERROR、それ以外の届かなさは WARNING」の線引きになるが、ボット対策の 403 を WARNING にすると、本当に消えたページを 403 で隠すサイトを見逃す。
- **403 の扱い。** github.com の 403 は実行環境のプロキシ由来か GitHub 側の制限かを区別できていない。ハーネスの実行環境に依存する誤判定を、ハーネスの側でどこまで吸収するか。

## 再考（2026-09-29）: HEAD の 5xx

tommy-farm に出典を 1 件（e-種や の商品ページ `https://www.e-taneya.com/item/002796`）足して `kb validate --check-urls --for` を回したところ、`unreachable URL` の ERROR になった。ハーネスと同じ UA で確かめ直すと、HEAD は 500、GET は 200 だった。ページは実在する。

(g) で 404 を GET の再確認に足したが、再確認の対象を「HEAD が返しうる誤った応答」の列挙で決めている限り、列挙から漏れた応答で同じ誤判定が繰り返される。今回は 500 がそれに当たる。R6 のテストは「HEAD が 500 なら GET にフォールバックせず到達不能」を固定していた。

**対応の選択肢**

- (i) 再確認の対象に 500 を足す（または 5xx 全体を足す）。列挙を広げるだけで、次に 400 や 501 を返すサイトが出れば同じことになる。
- (j) HEAD が HTTP のエラー応答（`HTTPError`）を返したら、状態コードを問わず GET で確かめ直す。HEAD は GET を省くための近道と位置づけ、到達の判定は GET の結果で下す。
- (k) HEAD をやめて最初から GET を送る。本文を読まずに閉じても、応答の大きいページで転送量と時間が増える。HEAD が 200 を返すサイトが大半なので、近道を捨てる理由がない。

**判断**

- **今やる: (j)。** 代償は、本当に消えたページや壊れたサーバに GET を 1 回余分に送ることだけである。(g) と同じ理由で、誤判定を減らす利益の方が大きい。R6 で固定した「HEAD が 500 なら到達不能」のテストは、「HEAD が 500 でも GET が 200 なら到達可能」「両方 500 なら到達不能」に置き換える。
- **見送る: (i)。** 列挙の漏れを繰り返すため。
- **見送る: (k)。** 再開条件は、HEAD が 200 を返すのに GET では届かない（HEAD を信じると誤って到達可能とする）サイトが実例として出たとき。
- タイムアウトや接続失敗など、HTTP の応答が無い失敗は (j) の対象にしない。GET を送っても同じ理由で失敗する見込みが高く、待ち時間が倍になる。扱いは未決事項の「一時的な失敗を ERROR にするか」に残す。GET も 5xx を返す場合も、同じ未決事項の範囲である。

## 実装の記録

2026-09-27 に判断どおり (a)(d)(e)(g) を実装した（コミット 9ec3f09）。

- `check_urls()` に `entities` / `ref_ids` 引数を足し、`kb validate` に `--for` / `--ref` を足した。出典の集め方は `references.entity_reference_ids()`（`kb reference show --for` と同じ関数）を使い、規則を二重に持たない。
- 並列化は `ThreadPoolExecutor`（全体 8 本、同じホストへは 2 本）。確認対象を走査順に集めてから並列に確かめ、結果を走査順に並べ直して報告する。
- `_url_reachable()` の GET 再確認の対象に 404 を足した。
- add-entity は `--for`、find-book / find-paper は `--ref` で絞る手順にした。

omnibus-kb で同じ条件のまま測り直した。

| 実行 | 変更前 | 変更後 |
|---|---|---|
| KB 全体（`--check-urls`） | 約 305 秒 | 約 42 秒 |
| 追加した 1 件だけ（`--check-urls --for`、検証本体を含む） | なし（全体を確かめるしかなかった） | 約 7 秒 |

KB 全体の ERROR は 12 件になった。tower.jp と greensnap.jp の誤判定は消えた。残りは HEAD も GET も 403 の 10 件と、今回は中国のサイト 2 件が一時的な失敗として出ており、未決事項の分類どおりである。

**当初の判断から変えた点**

- `scripts/validate.py` には `--for` / `--ref` を足さなかった。導入先のスキルはすべて `kb validate` を呼んでおり、互換入口に同じオプションを増やす利用者がいない。HEAD 404 の再確認と並列化は共通の `check_urls()` にあるので、`scripts/validate.py --check-urls` にも効く。
