# KB への問い合わせに答える

このスキルは、利用者の問いに KB を根拠として答えるための手順である。特定のエージェントランタイムに依存しない。使う道具はファイルの読み取り、文字列検索、シェルでの `kb` コマンドの実行だけである。KB のファイルは読むだけで、エンティティ・出典・懸念・評価セットは書き換えない。検索器の実装や評価の代わりではない。検索・評価は kb-retrieval-core の責務であり、入っていれば使ってよい。無くてもこの手順だけで完結する。

型名・述語・タグは導入先の語彙が正本である。このスキル本文に出てくる述語（`created-by` / `part-of` など）は例であり、導入先にあるとは限らない。

## 原則

- **根拠は KB 内のファイルだけ。** KB に書かれていないことを学習知識で埋めて、KB の内容として答えない。
- **KB に無いことは「KB には記載がない」と答える。** 答えられないことは失敗ではない。
- **KB の外の知識で補足する場合は分ける。** 利用者が望む場合や、答えの理解に欠かせない場合に限り、KB の内容とは別の節に「KB の外の知識（未検証）」と明記して書く。
- **確度を落とさない。** 出典の食い違い・確度の低い関係・`disputed` の Claim を、断定に書き換えない。

## 準備

1. リポジトリルートの `kb-domain.yml` から `content_root`、`views.root`、`concerns.root` を確認する。
2. 導入先の `AGENTS.md` の型の使い分けを読む。特に、`Note` のように整理前の記録を置く型があれば、その記述を確定した知識として扱わない。

## 探す

次の順で探し、該当するエンティティを絞る。1 つの経路で見つからなくても、次の経路を試す。

1. **名前で引く。** `<content_root>` 配下の frontmatter の `title` と `aliases` を文字列検索（grep・rg など、使えるもの）で引く。表記ゆれ（全角・半角、カタカナ・英字、略語）を変えて試す。
2. **説明と分類で引く。** `description`、`tags`、`<content_root>/index.md` の分野別一覧、各ディレクトリの `index.md` を見る。
3. **本文で引く。** 本文を語句で文字列検索する。本文での言及は、その語を題にしたエンティティが無いことを示す手がかりにもなる。
4. **関係を辿る。** 作り手・所属・由来・系譜・関連を問う場合、答えは本文ではなく relations の先にあることが多い。ルートの `graph.json` の `edges`（`source` / `predicate` / `target`）で、見つけたエンティティから 1〜2 段たどる。逆向き（「X が作ったもの」「X に属するもの」）は `target` 側から引く。述語の意味は `<content_root>/vocabulary.yml` で確かめる。
5. **束ねを見る。** 列挙の問い（「〜を全部挙げよ」）は、`views.root` があれば `kb view list` で関係するビューを探し、`kb view resolve <id>` でメンバーを引く。ビューは書き手が見出した束ねなので、ビューの `description` と `basis` を答えに添える。
6. **検索器があれば使う。** 導入先が kb-retrieval-core などの検索器を入れていれば、その結果を候補として加える。候補は必ず本文を読んで確かめる。

`graph.json` が古い可能性があれば `kb sync --check` で確かめる。古ければ生成し直さず、Markdown の frontmatter の `relations` を正として読む。

## 読む

候補のエンティティごとに次を読む。

- 本文と frontmatter（`relations`、型固有の時間のフィールド、`same_as`）。relations の確度 `confidence` は frontmatter にだけあり、`graph.json` の `edges` には無い。答えに使う関係は、始点のファイルの frontmatter で確度を確かめる。
- 出典: `kb reference show --for <エンティティのパス>` で、`sources` と本文の「（出典: id）」が引く書誌を得る。`references.yml` を丸ごと読まない。
- 懸念: `concerns.root` があれば `kb concern list --for <エンティティのパス>` で、対象の懸念を読む。答えに使う出典にも `kb concern list --for "ref: <id>"` を当てる。
- Claim: 答えに関わる Claim があれば `kb claim list` で `status` を確かめる。

本文中のリンクは、問いに関係するものだけたどる。

## 答える

答えは次の形にする。

1. **答え。** 問いへの直接の答えを先に書く。各文の根拠になったエンティティへ、リポジトリルートからの相対リンク（`[title](<content_root>/dir/file.md)`）を付ける。
2. **根拠。** 使った出典を、`ref: <id>` と書誌（著者・題・年、あれば URL）で挙げる。Web 出典の URL 文字列はそのまま示す。
3. **確度と注意。** 次があれば必ず書く。
   - 答えに使った懸念（ID・`kind`・`status`・要旨）。`status` が未解決のものは、どちらの記述も断定しない。
   - 確度 C / D の関係（「〜の関係は確度 C（公式資料のみ）」のように）。
   - `disputed` / `proposed` の Claim。
   - 整理前の型（`Note` など）だけに基づく記述。
4. **KB に無いこと。** 問いのうち KB で答えられなかった部分を、「KB には記載がない」と明記する。どこまで探したか（引いた名前・たどった関係）を 1 行で添える。
5. **KB の外の知識（任意）。** 上の原則に従う場合だけ、別の節に分けて書く。

問いが KB の複数のエンティティにまたがる比較・列挙・年代の問いでは、答えを組み立てた経路（どのエンティティからどの関係をたどったか）も示す。

## 答えられなかったとき

KB の欠落が分かった場合は、答えの末尾に、欠落の種類を次の語で 1 つ示す。導入先の `evals/rag-eval.yml` の `gap` と同じ語彙である。

- `missing-entity` … エンティティ自体が未収録
- `missing-relation` … エンティティはあるが関係が欠けている
- `missing-text` … 本文の記述が不足している
- `retrieval` … 記述はあるが、title・aliases・description・tags・リンクが弱く、探しにくかった

利用者が望めば、導入先の `docs/BACKLOG.md` へ積む 1 行の案を示す（出所は「問い合わせ」）。`evals/rag-eval.yml` に固定の問いとして足すかは人が選ぶので、このスキルは追記しない。案として `id` を除いたエントリ（`kind` / `query` / `expected` / `evidence`）を示すに留める。欠落を埋める作業は `expand-kb` スキルが担う。
